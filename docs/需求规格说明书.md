## 1. 引言

### 1.1 编写目的

本文档旨在为FaceGuard人脸识别管理系统提供完整、清晰、无歧义的需求规格说明。作为产品经理、开发团队、测试团队、设计团队及所有项目干系人之间的沟通基础，本文档将明确系统的功能范围、质量标准和技术边界，确保各方对产品需求形成一致理解，并为后续的设计开发、测试验证和产品验收提供法定依据。

本文档的预期读者包括：产品负责人（用于需求确认和优先级决策）、开发团队（用于技术方案设计）、测试团队（用于测试用例设计）、运维团队（用于部署和运维支持），以及项目管理者（用于进度控制和范围管理）。

### 1.2 项目背景

随着人工智能技术在计算机视觉领域的快速发展，人脸识别已从实验室走向广泛的商业应用。在当前市场环境下，企业内部管理、校园考勤体系、园区门禁系统等场景对智能化身份认证解决方案的需求持续增长。传统的密码验证、门禁卡等方式存在口令遗忘、卡片丢失、身份冒用等安全隐患，已难以满足现代组织对安全性和便捷性的双重需求。

FaceGuard项目正是在这一背景下应运而生，旨在构建一套轻量化、高可用的人脸识别身份管理平台。项目的核心价值主张是"即部署、即使用"的一站式解决方案，通过降低智能化升级的技术门槛和实施成本，让更多中小型组织能够享受人工智能带来的便捷体验。

### 1.3 范围界定

**系统核心功能范围包括**：用户身份注册与认证、人脸数据采集与管理、基于人脸识别的身份验证、管理员后台系统（含用户管理、安全审计、系统配置）。

**系统明确不包括以下功能**：人事管理系统集成、门禁硬件控制集成、考勤数据导出功能、移动端原生应用开发、陌生人人脸图像存储以外的隐私保护功能。

### 1.4 定义与缩略语

为确保文档内容清晰无歧义，本节列出文档中使用的专业术语及其定义：

- **B/S架构**：Browser/Server Architecture，浏览器/服务器架构模式，客户端通过Web浏览器访问服务端应用
- **Haar级联分类器**：基于Viola-Jones框架的人脸检测算法，通过预训练模型识别图像中的人脸区域
- **LBPH算法**：Local Binary Patterns Histogram，局部二值模式直方图算法，用于提取人脸纹理特征进行身份识别
- **RBAC**：Role-Based Access Control，基于角色的访问控制模型
- **Session**：服务端会话机制，用于在无状态HTTP协议上维护用户登录状态
- **Base64**：一种基于64个可打印字符表示二进制数据的编码格式，常用于浏览器与服务端传输图像数据
- **UVC**：USB Video Class，USB视频设备通用驱动程序标准

## 2. 综合描述

### 2.1 产品前景

FaceGuard的定位是一款面向中小企业、教育机构、住宅小区、产业园区等场景的轻量化人脸识别身份管理系统。在当今数字化转型的浪潮中，组织对于安全、便捷、智能的身份验证方式有着迫切需求。传统门禁卡容易丢失和借用，密码容易被遗忘和破解，而人脸识别技术能够实现"看一眼就通过"的无感通行体验，大幅提升安全等级和通行效率。

从市场竞争格局来看，目前市面上的人脸识别解决方案主要分为两类：一类是大型企业部署的 комплексные решения，硬件和软件成本高昂，需要专业团队运维；另一类是轻量级的SaaS服务，数据需要上云，存在隐私安全顾虑。FaceGuard的差异化定位是：提供介于两者之间的"私有化部署、轻量化运维"的解决方案，既保证数据本地化存储的安全性，又降低部署和运维的技术门槛。

系统的目标用户群体分为两类：普通用户是组织内部的员工或成员，主要使用人脸识别完成日常考勤打卡或门禁通行；管理员是组织的行政人员或IT运维人员，负责用户账号管理、安全审计和系统参数配置。两类用户在系统中拥有不同的权限范围和功能访问权限。

### 2.2 系统架构概览

FaceGuard采用业界标准的B/S（Browser/Server）三层架构模式构建。这种架构的核心优势在于：客户端无需安装专用软件，任何现代Web浏览器均可访问；所有业务逻辑和数据处理集中在服务端，利于统一管理和安全控制；系统升级仅需更新服务端，客户端自动适配。

系统的技术栈组成如下：后端采用Python语言配合Django Web框架，Python在计算机视觉领域拥有最丰富的生态，Django提供了完善的MTV架构模式和内置的安全机制；计算机视觉部分采用OpenCV库，实现Haar级联分类器人脸检测和LBPH人脸识别算法；数据存储采用MySQL关系数据库存储结构化数据，文件系统存储人脸图像和识别模型文件；前端采用原生HTML5、CSS3和JavaScript实现，通过浏览器原生API调用摄像头。

系统整体架构分为表现层、业务逻辑层和数据层三层。表现层负责页面渲染、用户交互和摄像头调用；业务逻辑层负责请求处理、身份认证、业务流程控制和算法调用；数据层负责数据持久化存储和文件管理。三层之间通过HTTP协议和RESTful API进行通信。

![技术架构图](./images/架构图3.png)

### 2.3 用户特征与使用场景

系统面向的主要用户群体可分为普通用户和管理员两类，每类用户具有明确的角色特征和使用场景。

普通用户的典型使用场景是日常上下班时的门禁通行。用户到达门禁前，摄像头自动捕捉人脸图像，系统在本地人脸库中查找匹配用户，确认身份后自动放行。整个过程用户无需停留、无需接触任何设备，实现了真正的无感通行。对于尚未录入人脸的用户，系统也提供传统的账号密码登录方式作为备选。

管理员的核心职责是保障系统安全稳定运行。管理员需要定期查看操作日志，了解系统使用情况；需要处理陌生人告警，核实未授权访问事件；需要管理系统用户账号，包括新增用户、删除离职用户；需要根据实际运行情况调整识别阈值等系统参数。

## 3. 功能需求

### 3.1 身份认证模块

身份认证是FaceGuard的核心功能模块，决定了系统的安全性和易用性。本模块包含账号密码认证和人脸识别认证两种方式，用户可根据实际情况灵活选择。

#### 3.1.1 账号密码认证

**功能概述**

账号密码认证是系统提供的基础身份验证方式。所有在系统中注册的用户都拥有独立的账号和密码，可以通过输入正确的凭证完成登录。这种认证方式不依赖摄像头设备，适用于任何支持Web浏览器的终端设备。

**用户故事**

作为已注册用户，我希望通过输入账号和密码登录系统，以便在不方便使用人脸识别时仍能正常访问系统功能。

**业务描述**

用户访问系统登录页面，输入已注册的账号和设定的密码后提交请求。系统接收到登录请求后，首先验证账号是否存在，若不存在则返回"用户不存在"的提示；若账号存在，则进一步验证密码是否正确，密码错误时返回"账号或密码错误"的提示。验证通过后，系统创建服务端会话并将SessionID以Cookie形式返回客户端，后续请求通过Session验证用户身份。

**异常处理**

系统对以下异常情况进行处理：用户输入的账号不存在时，提示用户检查账号是否正确或选择注册新账号；用户输入的密码错误时，提示用户检查密码是否输入正确，密码连续错误达到5次时建议用户使用"找回密码"功能；用户账号已被管理员禁用时，提示用户联系管理员处理。

#### 3.1.2 人脸识别认证

**功能概述**

人脸识别认证是系统提供的核心特色功能，利用计算机视觉技术通过人脸特征比对完成身份验证。用户无需输入任何文字，仅需面对摄像头完成刷脸即可登录。这种认证方式实现了"零接触、秒级通过"的用户体验，特别适合频繁进出的门禁场景。

**用户故事**

作为已完成人脸注册的用户，我希望通过摄像头刷脸登录系统，以便省去输入账号密码的繁琐步骤，实现快速通行。

**业务流程**

人脸识别登录的整体流程包括以下几个关键步骤：

首先，系统调用浏览器摄像头获取实时视频流，并在页面中显示视频预览画面。用户确认画面中自己的脸部位置清晰可见后，点击"开始识别"按钮或等待系统自动检测到人脸后自动触发识别。系统截取当前视频帧作为待识别图像，并进行预处理操作，包括灰度转换、直方图均衡化等，以提高后续识别算法的准确性。

然后，系统调用Haar级联分类器在预处理后的图像中检测人脸区域。若画面中未检测到人脸，则提示用户"未检测到人脸，请确保正对摄像头"；若画面中检测到多个人脸，则自动选择尺寸最大、位置最居中的人脸进行后续识别。

接着，系统利用LBPH算法提取检测到的人脸区域的纹理特征，与本地人脸库中已注册用户的特征进行逐一比对。系统返回最佳匹配结果及其匹配分数。

最后，系统将匹配分数与预设阈值进行比较。若分数低于阈值，说明识别成功，系统创建会话并返回登录成功；若分数高于阈值，说明未能匹配到注册用户，系统记录陌生人告警并返回"未识别到注册用户"的提示。

![人脸识别登录流程图](./images/架构图4.png)

**阈值调整说明**

识别阈值是控制系统安全性的关键参数。阈值越低，识别越严格，误识率越低但拒识率越高；阈值越高，识别越宽松，误识率越高但拒识率越低。系统默认阈值设置为70，适用于一般办公场所。对于高安全需求场所，建议将阈值调整为55以下；对于人流量大的场所，可适当提高阈值至85以上以提升通行效率。

#### 3.1.3 会话管理

**功能概述**

会话管理机制用于在无状态的HTTP协议上维护用户的登录状态，确保用户在一段时间内的多次请求能够被识别为同一用户。

**机制描述**

用户登录成功后，服务端创建一个Session数据对象，用于存储用户ID、账号、角色等身份信息。SessionID作为这个数据对象的唯一标识，以HttpOnly Cookie的形式返回给客户端浏览器。由于Cookie设置了HttpOnly属性，JavaScript脚本无法读取SessionID，这有效防止了跨站脚本攻击（XSS）窃取用户会话的风险。

会话默认超时时间设置为30分钟。若用户在该时间范围内没有任何操作行为，服务端自动销毁Session，用户需要重新登录。若用户在超时前有操作行为，则会话自动续期。

用户主动点击"退出登录"按钮时，服务端立即销毁Session并清除客户端Cookie，确保会话及时失效。

### 3.2 用户管理模块

用户管理模块负责处理用户账号的全生命周期管理，包括新用户注册、个人信息维护等功能。

#### 3.2.1 用户注册

**功能概述**

用户注册是用户获取系统访问权限的唯一入口。新用户通过填写必要的身份信息完成账号创建，成为系统的合法用户。

**用户故事**

作为潜在的系统用户，我希望通过填写基本信息完成账号注册，以便后续使用系统提供的人脸识别服务。

**业务流程**

用户访问系统注册页面，填写所需的账号信息。系统要求填写的内容包括：用户账号（用于登录，长度1至20个字符）、登录密码（安全凭证，最少6个字符）、用户姓名（真实姓名，用于显示和记录）、性别（用于系统统计和个性化展示）。手机号码作为选填项，用户可选择是否提供。

用户提交注册信息后，系统进行以下校验：账号是否为空且长度是否符合要求；密码是否为空且长度是否达到最低要求；姓名是否填写；性别是否选择。校验不通过时，系统返回相应的错误提示，用户修改后重新提交。

校验通过后，系统检查账号的唯一性。若账号已被其他用户注册，系统返回"该账号已注册，请更换账号"的提示；若账号可用，系统将用户信息写入数据库，完成注册流程。

![用户注册流程图](./images/架构图5.png)

**密码安全说明**

用户密码在传输过程中通过HTTPS加密保护，存储时采用SHA-256算法进行哈希处理。系统数据库中不存储明文密码，即使数据库被非法访问，攻击者也无法还原出用户的原始密码。

#### 3.2.2 个人信息管理

**功能概述**

个人信息管理允许用户查看和修改自己的基本信息，确保用户信息的时效性和准确性。

**用户故事**

作为已登录用户，我希望查看和修改自己的个人信息，以便保持信息的准确性和时效性。

**功能描述**

用户登录后可以访问个人信息页面，查看自己注册时填写的各项信息，包括账号、姓名、性别、手机号、人脸注册状态等。用户可以修改姓名和手机号，修改后系统更新数据库中的记录。

用户需要修改密码时，系统要求用户输入原密码进行验证，确保修改密码的操作确实是账号持有人发起。验证通过后，用户输入新密码完成修改。

### 3.3 人脸管理模块

人脸管理模块负责处理人脸数据的采集、存储、训练和管理，是人脸识别功能的数据基础。

#### 3.3.1 人脸数据采集

**功能概述**

人脸数据采集是用户录入自己的人脸样本的过程。系统需要采集足够数量和质量的人脸图像，才能训练出准确的识别模型。

**用户故事**

作为已注册用户，我希望通过摄像头采集并保存我的人脸照片，作为后续人脸识别的样本数据。

**采集流程**

用户进入人脸采集页面后，系统调用摄像头显示实时视频预览。用户调整坐姿和光线，确保面部正对摄像头、表情自然、面部清晰可见。确认准备就绪后，用户点击"拍照"按钮或等待系统自动检测到最佳拍摄时机后自动拍照。

系统截取当前帧图像后，首先进行人脸检测，验证画面中是否存在人脸且仅有一张人脸。若检测到多张人脸或无人脸，系统提示用户调整姿势后重新拍摄。

通过人脸检测后，系统对图像进行质量评估。评估指标包括：清晰度（通过拉普拉斯算子方差判断，值越高表示越清晰）、亮度（灰度均值在合理范围内，避免过曝或过暗）、人脸尺寸（人脸框宽高均不小于80像素，确保有足够特征信息）。若图像质量未达标，系统提示用户调整光线或距离后重新拍摄。

图像通过质量检测后，系统将其保存至该用户的人脸目录中。系统限制每个用户最多保存6张人脸样本图像，超出数量时提示用户删除旧样本后再采集。新样本保存成功后，系统更新该用户的人脸样本数量统计。

![人脸采集界面示意图](./images/架构图6.png)

**样本数量要求**

系统要求用户至少采集3张人脸样本才能进行模型训练。这个数量要求是为了确保识别模型能够学习到用户在不同光线、不同角度下的人脸特征，提高识别算法的鲁棒性。

#### 3.3.2 模型训练

**功能概述**

模型训练是系统根据用户已采集的人脸样本，训练生成可用于人脸识别的人工智能模型的过程。

**用户故事**

作为已完成人脸采集的用户，我希望系统根据我的人脸样本训练识别模型，以便后续能够通过人脸识别方式登录系统。

**训练流程**

用户在人脸管理页面点击"训练模型"按钮发起训练请求。系统首先检查该用户已采集的样本数量，若不足3张，训练无法进行，系统提示用户继续采集人脸照片。

样本数量满足要求后，系统读取该用户目录下所有的人脸图像，利用OpenCV的LBPH算法进行模型训练。训练过程包括：对每张图像进行LBP编码、统计各区域的直方图特征、合并所有样本特征生成识别模型。训练完成后，系统将模型参数保存至该用户目录下的trainer.yml文件中，并更新用户的人脸注册状态为"已注册"。

**模型更新机制**

用户可以随时采集新的样本图像，并重新触发模型训练。新训练的模型会覆盖旧的模型文件，确保识别模型反映用户最新的人脸特征状态。

#### 3.3.3 人脸数据删除

**功能概述**

人脸数据删除允许用户或管理员删除已存储的人脸样本和训练模型，释放存储空间或保护隐私。

**功能描述**

用户可以在个人中心发起人脸数据删除请求，系统将该用户目录下的人脸图像和模型文件全部删除，并重置人脸注册状态为"未注册"。删除后，用户需要重新进行人脸采集和模型训练才能恢复人脸识别功能。

管理员可以在后台管理界面删除任意用户的人脸数据，用于处理用户隐私请求或安全事件。

### 3.4 系统管理模块（管理员功能）

系统管理模块是管理员专属的功能区域，用于系统的日常运维和安全管理工作。

#### 3.4.1 用户管理

**功能概述**

用户管理功能允许管理员对系统中的用户账号进行集中管理，是系统运维的基础功能。

**用户故事**

作为系统管理员，我希望查看和管理所有用户账号，以便进行日常运维和用户服务工作。

**功能描述**

管理员登录后可以访问用户管理页面，查看系统中所有已注册用户的列表。列表默认按照注册时间倒序排列，显示每个用户的账号、姓名、性别、人脸注册状态等信息。

管理员可以通过输入账号或姓名的关键字进行搜索，快速定位目标用户。点击用户记录可以查看该用户的详细信息，包括注册时间、人脸样本数量、最近登录时间等。

管理员可以删除普通用户账号。删除操作不可恢复，用户的账号信息、操作日志（保留副本）、登录记录将被移除，人脸数据文件也将被删除。

管理员无法删除自己的账号，也无法将普通用户提升为管理员或将自己降级为普通用户，这些操作需要直接修改数据库进行。

#### 3.4.2 操作日志

**功能概述**

操作日志功能用于记录系统中所有用户的操作行为，为安全审计提供数据支持。

**用户故事**

作为系统管理员，我希望查看所有用户的操作记录，以便进行安全审计和责任追溯。

**功能描述**

系统自动记录所有通过API发起的请求，包括请求的用户账号（未登录请求记录为"匿名"）、请求时间、请求方法、请求路径、请求参数、处理时长和来源IP地址。这些日志数据对于追踪用户行为、分析系统性能、调查安全事件具有重要价值。

管理员可以在日志查询页面按时间范围、用户名等条件进行筛选查看。日志数据保留期限建议设置为6个月，超期日志可由管理员手动清理或配置自动归档策略。

#### 3.4.3 安全告警管理

**功能概述**

安全告警功能用于记录和处理陌生人试图通过人脸识别访问系统的安全事件。

**用户故事**

作为系统管理员，我希望查看陌生人访问记录，以便及时发现和处理未授权访问事件。

**触发机制**

当用户使用人脸识别方式登录时，若系统未能匹配到任何已注册用户（匹配分数全部高于阈值），系统判定此次尝试为陌生人访问。此时系统自动记录一条告警信息，包括尝试时间、来源IP地址、截取的人脸图像、匹配分数等。

**功能描述**

管理员可以在告警管理页面查看所有陌生人访问记录。告警记录按时间倒序排列，最新的告警显示在最前面。每条告警记录可查看详细信息，包括发生时间、来源IP、人脸截图、匹配分数等。

管理员处理完某条告警后，可以将其标记为"已处理"或直接删除。系统建议管理员定期清理已处理的告警记录，保持告警列表的有效性。

#### 3.4.4 系统参数配置

**功能概述**

系统参数配置功能允许管理员调整系统运行的关键参数，以适应不同部署环境和使用场景的需求。

**配置项说明**

系统目前支持配置的核心参数是识别阈值（face_threshold）。该参数控制人脸识别成功与否的判定标准，默认值为70，管理员可根据实际需求调整至40至100之间的任意整数。

阈值调整后，新的阈值立即生效，无需重启服务或重新训练模型。建议管理员在调整阈值前评估对用户体验和安全性的影响，必要时可以先在小范围内测试新阈值的实际效果。

## 4. 非功能需求

### 4.1 性能需求

系统性能直接影响用户体验和管理效率，因此对关键操作设定以下性能指标：

| 性能指标 | 具体要求 | 说明 |
|----------|----------|------|
| 账号密码登录响应时间 | ≤3秒 | 从提交到页面跳转完成 |
| 人脸检测单次处理时间 | ≤500毫秒 | 识别流程中计算量最大的步骤 |
| 完整人脸识别登录时间 | ≤1秒 | 从触发识别到返回结果 |
| 支持并发在线用户数 | ≥50个 | 该压力下各项指标仍满足要求 |
| 服务端内存占用 | ≤500MB | 正常运行状态 |

**并发能力说明**：若实际用户量超过50人，建议通过水平扩展增加应用服务器实例进行负载均衡。

**资源占用说明**：内存主要包括Python进程、Django框架开销、OpenCV模型加载和数据库连接池。

### 4.2 安全性需求

**密码安全**

用户密码采用SHA-256算法进行不可逆哈希存储，数据库中不保存明文密码。生产环境部署时应启用HTTPS加密传输，防止密码在网络传输过程中被窃取。系统对密码长度设置最低要求为6个字符，鼓励用户设置更复杂的密码。

**会话安全**

用户登录成功后，服务端创建Session并存储用户身份信息，客户端仅保存SessionID。SessionID通过HttpOnly Cookie传输，防止JavaScript脚本读取。会话超时时间设置为30分钟，超时后自动失效。

**权限控制**

系统采用基于角色的访问控制（RBAC）模型。普通用户只能访问和操作本人的数据，无法查看或修改其他用户的信息。管理员拥有额外的系统管理权限，可以访问用户管理、日志查询、告警管理等管理员功能。

**数据保护**

系统采用Django ORM进行数据库操作，所有SQL语句通过参数化查询执行，自动防止SQL注入攻击。Django模板引擎对输出变量进行HTML自动转义，防止跨站脚本攻击（XSS）。

### 4.3 可靠性需求

**系统可用性**

系统在正常运行环境下的可用性应达到99%以上。这意味着在非计划维护窗口期间，系统应保持正常运行。系统设计为单点故障后能够快速重启恢复，减少宕机时间。

**错误处理**

系统对各类异常情况进行友好处理，不向用户暴露技术细节和系统内部状态。错误信息应表达清晰，帮助用户理解发生了什么问题以及如何解决。关键操作（如登录、数据提交）失败时，系统提供明确的失败原因和重试建议。

**数据一致性**

涉及多个数据表的复合操作使用数据库事务进行包装，确保数据要么全部成功，要么全部回滚，避免出现数据不一致状态。人脸图像保存和数据库记录更新作为原子操作处理。

### 4.4 兼容性需求

**浏览器兼容性**

系统前端代码应兼容以下浏览器：Google Chrome 80及以上版本、Mozilla Firefox 75及以上版本、Microsoft Edge 80及以上版本、360安全浏览器12及以上版本。这些浏览器版本对HTML5、CSS3和ECMAScript 6的支持已经成熟，能够保证页面的正常显示和交互功能。

**操作系统兼容性**

服务端支持部署在Windows 10/11和Linux（Ubuntu 18.04及以上）操作系统上。Python和Django对这两个平台都有良好的支持，部署流程差异较小。

**硬件兼容性**

客户端摄像头需要支持UVC标准协议，这是绝大多数现代USB摄像头的通用标准。摄像头像素建议720P以上，以获得足够清晰的人脸图像用于识别。

### 4.5 运行环境需求

**服务端运行环境**

CPU建议使用Intel Core i5第10代或以上处理器，以支持AVX指令集加速OpenCV计算。内存推荐16GB，以满足多用户并发和模型加载需求。硬盘推荐256GB SSD，以获得更快的IO性能，满足大量小文件读写需求。

**网络环境**

开发测试阶段可使用普通百兆网络。生产环境建议部署在千兆网络环境下，以应对大量图片数据传输的场景。

## 7. 验收标准

### 7.1 功能验收条件

**身份认证功能**

用户注册功能应允许新用户填写账号、密码、姓名、性别信息完成注册。系统应对账号唯一性进行校验，对密码长度进行验证。账号密码登录功能应正确识别有效凭证并拒绝无效凭证。人脸识别登录功能应能够识别已注册用户并拒绝陌生人。识别分数应能正确反映匹配程度，低于阈值时识别成功，高于阈值时识别失败。

**人脸管理功能**

人脸采集功能应能调用摄像头并显示预览画面。检测到人脸后可保存照片。单用户样本数量上限为6张应正确执行。模型训练功能应在样本数量达到3张或以上时成功启动训练，样本不足时提示用户。训练完成后用户的人脸注册状态应更新为已注册。

**系统管理功能**

管理员应能查看所有用户列表和详细信息。应能通过关键字搜索定位目标用户。应能删除普通用户账号。操作日志应完整记录所有请求。告警管理应能查看所有陌生人记录和详情。识别阈值配置应能成功修改并立即生效。

### 7.2 性能验收条件

系统登录响应时间应不超过3秒。人脸检测单次处理时间应不超过500毫秒。在正常光照、正脸条件下，人脸识别成功率应不低于95%。

### 7.3 界面验收条件

页面布局应合理美观，元素对齐，无明显错位。文字显示应清晰可读，无乱码。操作按钮应有明确的状态变化反馈，提交后应有结果提示。错误信息应表达清晰，不暴露技术细节。摄像头调用应有授权提示，权限拒绝时应提供友好引导。

### 8.2 术语表

本文档中使用的专业术语及其完整定义汇总如下：

Haar级联分类器是一种基于机器学习的对象检测算法，由Paul Viola和Michael Jones在2001年提出，广泛用于人脸检测领域。该算法通过级联的弱分类器组合实现高速准确的人脸区域定位。

LBPH算法即局部二值模式直方图算法，是一种基于纹理特征的人脸识别方法。该算法通过比较像素与其邻域的灰度关系编码局部纹理信息，统计各区域的直方图特征形成人脸描述符。

B/S架构是Browser/Server架构的缩写，是一种服务端提供数据处理能力、客户端通过浏览器访问的软件架构模式。相比传统的C/S架构，B/S架构无需客户端安装和维护，部署集中，升级方便。

Session即用户会话，是在无状态的HTTP协议上维持用户状态的技术机制。服务端创建Session存储用户身份信息，客户端通过SessionID标识会话。

RBAC即基于角色的访问控制，是一种广泛使用的权限管理模型。该模型将权限分配给角色，再将角色分配给用户，简化权限管理工作。

### 8.4 实现对照（V1.1 增量）

以下条目与当前代码实现一致，供验收与测试引用：

| 需求项 | 实现说明 |
|--------|----------|
| 人脸采集 | `POST /face/register`，质量分低于 40 拒绝入库 |
| 模型训练 | 每次成功采集后 `OpenCVFace._retrain()` 自动全量重训，生成 `lbph_model.yml` |
| 刷脸登录 | `POST /yonghu/faceLogin`，分数公式 `(100-confidence)*1.5`，与 `face_threshold` 比较 |
| 识别阈值 | 40～100，存于 `systemconfig.face_threshold`，默认 70 |
| 陌生人告警 | `POST /face/recognizeStranger` + `loginrecord.isstranger=1` |
| 登录审计 | 表 `loginrecord`，接口 `/face/loginRecord`、`/face/loginStats` |
| 双模认证 | 密码：`/yonghu/login`；人脸：`/yonghu/faceLogin` |
| 管理端 | 用户端 `server/templates/client/index.html`；可选 Vue `client/` |

详细接口见 [后端 API 接口文档](./后端API接口文档.md)。
